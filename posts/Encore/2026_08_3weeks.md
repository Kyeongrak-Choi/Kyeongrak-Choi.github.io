이번 주는 익숙한 개발 영역에서 조금씩 AI 쪽으로 넘어가는 경계에 있었던 것 같다.

FastAPI에서 PUT, PATCH, DELETE를 직접 구현하고 Router를 분리하면서 API 구조를 정리했다. 특히 PATCH에서 `exclude_unset=True`를 사용하는 이유가 기억에 남았다. 부분 수정이라는 개념 자체는 익숙하지만, 클라이언트가 실제로 전달한 필드만 골라 업데이트한다는 걸 Python 코드로 직접 보니 훨씬 명확했다. 언어나 프레임워크가 달라져도 결국 API를 설계할 때 고민하는 지점은 비슷했다.

반면 LLM 수업부터는 느낌이 달랐다. 이전까지는 개발 경험 덕분에 어느 정도 예상 가능한 내용이 많았다면, 토큰화부터 temperature, top_p, top_k 같은 샘플링 방식은 제대로 들여다본 적이 없는 영역이었다. 특히 같은 문장도 모델마다 토큰 수가 다르고, 공백이나 숫자까지 비용에 영향을 준다는 점이 재미있었다. 프롬프트 역시 단순히 질문을 잘 쓰는 문제가 아니라 결국 비용과 결과 품질을 같이 고려해야 하는 하나의 설계 대상이라는 생각이 들었다.

temperature와 top_p를 동시에 조절하지 않는다는 내용도 인상적이었다. 둘 다 결과의 다양성에 영향을 주지만 여러 값을 한꺼번에 바꾸면 무엇 때문에 결과가 달라졌는지 알기 어렵다. 개발할 때 변수를 하나씩 통제하면서 원인을 찾는 방식과 크게 다르지 않았다. AI라고 해서 완전히 다른 세계라기보다는 기존의 개발 습관을 적용할 수 있는 부분이 생각보다 많아 보인다.

마지막으로 PostgreSQL, Supabase, RDBMS까지 이어지면서 이제 각각 따로 배우던 것들이 조금씩 한 서비스 안에서 연결되기 시작했다. 아직은 개별 기술을 따라가는 단계지만 FastAPI, DB, LLM을 하나의 흐름으로 직접 묶어보면 지금 배우는 내용들이 훨씬 선명해질 것 같다.

### ✅ 4L

**👍 Liked**  
익숙한 API 개발에서 LLM이라는 새로운 영역으로 넘어가는 과정이 생각보다 재미있었다. 이미 알고 있는 개발 지식과 비교해볼 수 있어서 낯설어도 막막하지는 않았다.

**🤔 Lacked**  
토큰과 샘플링 파라미터는 개념으로는 이해했지만 아직 실제 결과가 얼마나 달라지는지 감이 부족하다. 직접 값을 바꿔가며 비교해볼 필요가 있다.

**📚 Learned**  
PATCH의 부분 수정 방식부터 LLM의 토큰 생성 과정까지, 결국 중요한 건 입력과 상태를 얼마나 명확하게 통제하느냐라는 공통점이 있었다.

**🚀 Longed for**  
FastAPI에 PostgreSQL이나 Supabase를 붙이고, 그 위에 실제 LLM 호출까지 연결해보고 싶다. 각각 따로 아는 것보다 한 번 끝까지 만들어보는 편이 지금은 더 도움이 될 것 같다.
