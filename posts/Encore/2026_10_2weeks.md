이번 주는 PlanEat 프로젝트를 마무리하면서 수업에서 배웠던 내용을 실제 서비스에 적용했을 때 어떤 문제가 생기는지 경험한 시간이었다. 그동안 LangGraph의 State와 Node, Tool 호출 흐름을 이해하는 데 집중했다면, 이번에는 직접 구현한 구조가 배포 환경에서도 제대로 동작하는지 확인해야 했다.

프로젝트에서 맡았던 LangGraph Orchestrator와 FastAPI를 연결하고, 여러 Tool의 결과를 받아 최종 응답을 만드는 과정은 생각보다 신경 쓸 부분이 많았다. 특히 Render에 서버를 배포한 이후 정상적으로 동작하지 않는 문제가 발생했는데, 처음에는 API 응답이나 타임아웃 문제를 의심했지만 실제 원인은 서버 메모리 부족이었다. 로컬에서 문제없이 동작하던 코드도 배포 환경의 리소스가 부족하면 제대로 실행되지 않는다는 걸 다시 확인했다.

모바일 개발을 하면서 메모리 관리의 중요성은 알고 있었지만, 서버 환경에서는 상대적으로 신경을 덜 썼던 것 같다. LangGraph와 여러 Tool, 외부 라이브러리를 함께 사용하는 구조인 만큼 실제 메모리 사용량을 고려했어야 했다. 문제의 원인을 정확하게 확인하기 전까지는 엉뚱한 부분을 수정할 수도 있다는 점도 이번에 다시 느꼈다.

프로젝트를 진행하면서 설계 단계에서 생각했던 흐름과 실제 구현 사이에도 차이가 있었다. State에 어떤 값을 유지할지, 사용자에게 추가 정보가 필요한 상황을 어떻게 처리할지, Tool에서 오류가 발생하면 어디서 대응할지 등 처음에는 단순해 보였던 부분들이 구현 과정에서 하나씩 고민거리가 됐다. 기존 개발 경험 덕분에 전체적인 구조를 이해하는 건 어렵지 않았지만, Python과 LangGraph로 옮기는 과정은 여전히 익숙하지 않았다.

이후 단일 Agent와 멀티 Agent의 차이를 비교하면서 프로젝트 구조를 다시 돌아보게 됐다. 처음에는 Agent가 여러 개면 더 발전된 구조처럼 보였지만, 실제로는 독립적인 판단이 필요한지가 더 중요한 기준이었다. PlanEat처럼 작업 흐름이 비교적 명확한 서비스라면 단일 Agent에 여러 Tool을 연결하는 방식이 오히려 적절할 수 있다.

이번 프로젝트를 통해 LangGraph를 직접 구현해봤다는 점은 만족스럽다. 다만 Python 코드를 완전히 이해하면서 작성했다고 말하기는 어렵고, 배포 환경의 리소스까지 충분히 고려하지 못한 부분은 아쉽다. 그래도 이번에는 단순히 기능을 완성하는 것에서 끝나지 않고, 실제로 서비스를 실행하고 문제를 확인하는 과정까지 경험했다는 점에서 의미가 있었다.

✅ 4L

👍 Liked | 좋았던 점

LangGraph를 이론으로만 배우지 않고 실제 프로젝트의 핵심 구조로 구현해봤다. 짧은 일정이었지만 설계부터 API 연결, 배포까지 경험한 게 가장 컸다.

🤔 Lacked | 부족했던 점

로컬 환경에서의 정상 동작에 집중한 나머지 배포 서버의 메모리와 리소스 제약을 충분히 고려하지 못했다. 문제가 발생했을 때도 처음부터 원인을 정확하게 파악하지 못한 점이 아쉽다.

📚 Learned | 새롭게 배운 점

서버 배포에서는 코드의 정상 동작뿐 아니라 실행 환경의 메모리와 리소스도 중요하다. 또 단일 Agent와 멀티 Agent의 차이는 Tool이나 Node의 개수가 아니라 독립적인 의사결정 주체가 몇 개인지에 있다는 점도 정리할 수 있었다.

🚀 Longed for | 앞으로 더 해보고 싶은 점

이번에 구현했던 LangGraph 코드를 다시 살펴보면서 State 관리와 예외 처리 부분을 개선해보고 싶다. 다음 프로젝트에서는 서버 리소스까지 고려해 설계하고, 배포 이후에도 안정적으로 동작하는 구조를 만들어보고 싶다.
