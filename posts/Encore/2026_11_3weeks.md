이번 주는 n8n을 이용해 여러 서비스를 연결하고, 실제로 활용할 만한 자동화 흐름을 만들어보는 데 집중했다. 지난주에는 기본적인 노드와 분기 처리를 익혔다면, 이번에는 Gmail, Discord, Telegram 같은 외부 서비스와 API를 연결하면서 n8n이 어떤 상황에서 유용한지 조금 더 구체적으로 알 수 있었다.

특히 뉴스 기사를 수집하고 LLM으로 필터링하거나, 사진을 분석해 칼로리를 기록하는 실습이 기억에 남는다. 단순히 데이터를 받아 다른 곳으로 전달하는 수준을 넘어 AI의 판단 결과를 다음 작업에 활용한다는 점이 흥미로웠다. 기존에 LangGraph로 구현했던 Agent와 비교하면 내부 구조를 세밀하게 제어하기는 어렵겠지만, 정해진 흐름을 빠르게 구성하는 데는 확실히 편했다.

여러 실습을 하다 보니 비슷한 노드를 반복해서 구성하는 경우도 있었다. 그래서 Subworkflow가 꽤 실용적으로 느껴졌다. 공통 기능을 별도의 워크플로로 분리하고 필요한 곳에서 호출하는 방식인데, 기존 개발에서 함수를 분리하거나 공통 모듈을 만드는 것과 크게 다르지 않았다. 오히려 이런 구조 없이 모든 작업을 하나의 워크플로에 넣으면 나중에는 수정하기가 더 어려울 것 같다.

일일 식단 리포트나 출장 도우미처럼 여러 단계를 연결하는 실습에서는 단순한 자동화와 Agent의 경계에 대해서도 생각해봤다. LLM이 포함됐다고 무조건 Agent라고 볼 수는 없고, 정해진 순서대로 실행하는 것과 상황에 따라 다음 행동을 결정하는 것은 구분할 필요가 있었다. 처음에는 n8n이 코드 없이 Agent를 만드는 도구라는 점에 관심이 갔지만, 지금은 어떤 작업을 자동화할지 먼저 판단하는 게 더 중요해 보인다.

Notion을 이용한 메모리 연동도 살펴봤다. 대화나 작업 결과를 외부에 저장하고 다시 활용하는 방식은 앞으로 개인 서비스를 고도화할 때도 참고할 만했다. 다만 저장된 정보를 언제 불러오고 얼마나 유지할지는 별도로 설계해야 할 문제다.

SQL 인젝션도 다시 정리했다. 개발 경력이 있다 보니 공격 방식 자체는 익숙했지만, LLM이 SQL을 생성하는 상황이라면 기존보다 더 신중하게 접근해야겠다는 생각이 들었다.

이번 주 실습으로 n8n에 대한 막연한 의문은 어느 정도 해소됐다. 그렇다고 모든 기능을 n8n으로 만들고 싶지는 않다. 복잡한 로직은 코드로 관리하고, 반복적인 연동 작업은 n8n을 활용하는 식으로 역할을 나누는 게 지금으로서는 가장 합리적으로 보인다.

✅ 4L

👍 Liked | 좋았던 점

Gmail, Discord, Telegram 등 여러 서비스를 직접 연결하면서 결과를 바로 확인할 수 있었다. 특히 LLM을 활용한 뉴스 필터링과 사진 분석은 실제 서비스에도 응용할 수 있을 것 같았다.

🤔 Lacked | 부족했던 점

실습에서는 주어진 흐름을 구현하는 데 집중해서, 오류가 발생하거나 외부 API가 응답하지 않을 때 어떻게 처리할지는 충분히 고민하지 못했다.

📚 Learned | 새롭게 배운 점

Subworkflow를 이용해 공통 기능을 분리하고 재사용하는 방법을 익혔다. Notion을 외부 메모리 저장소로 연동하는 방식도 살펴봤다.

🚀 Longed for | 앞으로 더 해보고 싶은 점

직접 만든 FastAPI 서버와 n8n을 연결해보고 싶다. Agent의 핵심 로직은 코드로 유지하면서 알림이나 정기 실행 같은 기능을 n8n으로 분리하면 실제로 얼마나 편해지는지 확인해볼 생각이다.
