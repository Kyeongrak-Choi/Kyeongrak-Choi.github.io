이번 주는 RAG를 본격적으로 배우면서 그동안 막연하게 알고 있던 '외부 문서를 찾아서 LLM에게 넘긴다'는 과정이 꽤 구체적으로 보이기 시작했다.

처음에는 문서를 Chunk로 나누고 Embedding한 뒤 Vector Store에 저장하고, 질문과 유사한 문서를 Retriever로 찾아 LLM에게 전달하는 전체 흐름을 정리했다. 구조 자체는 생각보다 단순했지만, 오히려 어려운 부분은 그다음이었다. 검색된 문서가 정말 좋은 문서인지, 질문 표현이 달라졌을 때 필요한 문서를 놓치지는 않는지 같은 문제가 생긴다.

Query Rewriting, Multi Query, RAG Fusion, Reranking을 연달아 보면서 RAG에서 중요한 건 Vector DB를 붙이는 것보다 결국 '검색 품질을 어떻게 높일 것인가'라는 생각이 들었다. 방법을 하나씩 추가하면 좋아 보이지만 검색 횟수와 비용, 응답 시간도 같이 늘어난다. 실제로 만들 때는 이것저것 다 넣는 것보다 어디까지 필요한지를 판단하는 게 더 중요할 것 같다.

SQLAlchemy나 Python의 클로저 같은 내용은 상대적으로 익숙했다. 문법은 여전히 한 번씩 찾아보지만 개념을 처음 배운다기보다는, 기존에 알고 있던 개발 방식을 Python에서는 어떻게 표현하는지 맞춰가는 느낌에 가깝다.

이번 주 후반에는 LangGraph와 Reducer를 보면서 다시 집중해야 할 지점이 생겼다. 마침 이번 프로젝트에서 내가 LangGraph 구현을 맡게 됐다. Node를 연결하는 것만으로 끝나는 게 아니라 어떤 State를 유지하고, 무엇을 누적하고 덮어쓸지까지 직접 결정해야 한다. 수업에서 배운 내용을 바로 프로젝트 구조로 옮겨야 하는 상황이라 부담도 조금 있지만, 오히려 제대로 익힐 기회라는 생각이 더 크다.

지금까지는 LLM이나 Agent의 전체 구조를 넓게 보는 쪽이었다면 이번에는 내가 맡은 영역이 명확하다. LangGraph는 이번 프로젝트에서 적당히 이해하고 넘어갈 수 있는 부분이 아니게 됐다. 구현을 맡은 만큼 그래프가 왜 이렇게 구성됐는지 설명할 수 있을 정도까지는 공부하고 싶다. 이번 프로젝트가 끝났을 때 단순히 코드를 완성했다기보다 LangGraph를 한 번 제대로 써봤다는 느낌은 남기고 싶다.

✅ 4L

👍 Liked
RAG의 검색 흐름부터 LangGraph의 State 관리까지 이어지면서 Agent 내부 구조가 이전보다 구체적으로 보이기 시작했다.

🤔 Lacked
RAG 검색 전략도 선택지가 많고 LangGraph도 아직 익숙하지 않다. 프로젝트에서는 결국 선택의 이유를 설명해야 하니 단순히 동작하는 코드를 만드는 것만으로는 부족할 것 같다.

📚 Learned
RAG에서는 어떤 Context를 가져올지가 중요하고, LangGraph에서는 그 데이터를 어떤 State로 들고 어떤 흐름으로 처리할지가 중요하다. 결국 모델 호출보다 그 주변의 설계가 점점 더 크게 보인다.

🚀 Longed for
이번 프로젝트에서 맡은 LangGraph 구현을 제대로 해보고 싶다. 수업 예제를 따라가는 수준에서 끝내지 않고 직접 State와 Node 흐름을 설계하면서 확실히 내 것으로 만들어야겠다.
