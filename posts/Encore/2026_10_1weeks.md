이번 주는 새로운 기술을 배우는 것보다 프로젝트를 실제로 구현하기 위한 준비에 더 많은 시간을 썼다. 이전까지는 LangGraph의 개념과 구조를 이해하는 데 집중했다면, 이제는 내가 직접 설계하고 구현해야 하는 상황이 됐다. 막상 프로젝트에 적용하려고 보니 수업에서 이해했다고 생각했던 것들도 다시 확인해야 할 부분이 꽤 많았다.

특히 LangGraph의 State와 Checkpoint를 공부하면서 대화형 Agent에서 상태 관리가 왜 중요한지 조금 더 구체적으로 이해하게 됐다. 사용자가 한 번에 모든 정보를 주는 게 아니라면 중간에 질문을 하고, 응답을 기다렸다가 이전 상태에서 다시 이어가야 한다. 단순히 Node를 연결하는 것보다 이런 흐름을 자연스럽게 처리하는 게 더 까다로워 보였다.

프로젝트에서는 LangGraph Orchestrator와 API Server를 맡게 됐다. 사용자 요청을 분석하고, 필요한 Tool을 호출하고, 결과를 정리해 응답하는 전체 흐름을 책임지는 역할이다. 기존 모바일 개발 경험 덕분에 API나 모듈 간 책임을 나누는 일은 익숙하지만, LLM의 판단이 중간에 들어가는 구조는 확실히 다르다. 예상하지 못한 응답이나 정보 부족 상황까지 고려해야 하니 일반적인 비즈니스 로직보다 변수가 많다.

기획 단계에서도 기능을 많이 넣는 것보다 역할과 인터페이스를 명확하게 정하는 데 신경을 썼다. 짧은 프로젝트인 만큼 처음부터 완벽한 구조를 만들 수는 없겠지만, 적어도 각 Node가 어떤 State를 읽고 반환하는지, Tool과는 어떤 데이터로 통신하는지 정도는 정리해두고 시작하고 싶었다. 가드레일이나 테스트도 중요하지만 구현 시간에 비해 과한 설계가 되지 않도록 조절하는 게 필요해 보인다.

이번 프로젝트는 아무래도 이전보다 부담이 있다. LangGraph를 맡겠다고 한 만큼 단순히 AI가 만들어준 코드를 연결하는 수준에서 끝내고 싶지는 않다. Python은 아직 익숙하지 않아 구현할 때 도움을 받는 부분이 많겠지만, 적어도 전체 실행 흐름과 설계 의도는 내가 설명할 수 있어야 한다고 생각한다. 이제는 공부한 내용을 실제 코드로 검증해볼 차례다.

✅ 4L

👍 Liked | 좋았던 점

LangGraph의 개념을 실제 프로젝트 구조에 대입해보면서 막연했던 부분들이 조금씩 구체화됐다. 특히 Orchestrator 역할을 맡으니 무엇을 우선적으로 공부해야 할지도 명확해졌다.

🤔 Lacked | 부족했던 점

구조를 설계하는 것과 Python으로 직접 구현하는 것 사이에는 아직 간격이 있다. 설계에 너무 많은 시간을 쓰다가 정작 구현과 테스트가 부족해지지 않도록 신경 써야겠다.

📚 Learned | 새롭게 배운 점

Checkpoint와 thread_id를 통해 Agent의 실행 상태를 유지하고 이어가는 방식을 이해했다. 대화형 Agent에서는 응답 생성뿐 아니라 중단과 재개까지 고려해야 한다는 점이 중요했다.

🚀 Longed for | 앞으로 더 해보고 싶은 점

이번에는 LangGraph의 State, Node, 조건부 분기, Tool 호출까지 직접 연결하고 싶다. 코드가 동작하는 것뿐 아니라 왜 이런 구조로 만들었는지 설명할 수 있는 수준까지는 가봐야겠다.
