이번 주는 AI Agent 자체보다는 Agent가 동작하는 환경과 운영 구조를 이해하는 데 더 많은 시간을 썼다. 지난 프로젝트에서 LangGraph를 구현하고 서버에 배포하면서 겪었던 문제들 때문인지, 이번에 배운 내용은 이전보다 실무적인 관점에서 보게 됐다.

컨텍스트 엔지니어링을 공부하면서 프롬프트를 잘 작성하는 것과 AI가 필요한 정보를 적절하게 제공받는 것은 별개의 문제라는 걸 알게 됐다. 단순히 많은 정보를 전달한다고 좋은 결과가 나오는 게 아니라, 현재 작업에 필요한 정보를 선별하고 유지하는 과정이 중요했다. 이전에 RAG나 LangGraph의 State를 배울 때는 각각의 기능으로 이해했는데, 이제는 이들이 결국 AI에게 어떤 정보를 언제 전달할지 결정하는 과정이라는 생각이 들었다.

AI Agent Harness도 비슷한 맥락에서 이해할 수 있었다. 모델이 다음 행동을 판단하더라도 실제 Tool을 실행하고, 결과를 전달하고, 실패했을 때 다시 시도하는 건 별도의 실행 구조가 담당한다. 지난 프로젝트에서 직접 구현했던 Orchestrator와 겹치는 부분이 많아서 개념 자체는 낯설지 않았다. 다만 그때는 기능을 완성하는 데 급급해서 실행 흐름을 얼마나 안정적으로 관리하고 있는지까지는 충분히 생각하지 못했던 것 같다.

Docker와 Kubernetes를 배우면서는 자연스럽게 서버 운영 쪽으로 관심이 옮겨갔다. Docker로 실행 환경을 이미지로 만들고, Kubernetes로 여러 컨테이너의 배포와 확장, 장애 복구를 관리한다는 구조는 이해하기 어렵지 않았다. 오히려 실제로 어느 규모부터 이런 구성이 필요한지, 작은 서비스에서도 도입할 이유가 있는지가 더 궁금했다.

특히 지난 프로젝트에서 서버 메모리 부족으로 배포에 문제가 있었던 경험이 떠올랐다. 당시에는 일단 서비스를 정상적으로 실행하는 게 우선이었지만, 지금 생각하면 서버 리소스와 실행 환경을 미리 확인했어야 했다. 모바일 개발에서도 성능과 메모리는 익숙한 문제인데, 서버에서는 비슷한 원칙을 다른 방식으로 적용해야 한다는 점이 흥미로웠다.

AWS 배포 실습까지 이어지면서 AI Agent 개발이 단순히 LLM을 연결하는 작업은 아니라는 생각이 더 확실해졌다. Python이나 인프라 도구는 아직 익숙하지 않지만, 기존 개발 경험 덕분에 왜 이런 기술이 필요한지는 조금씩 연결되고 있다. 당장 Kubernetes까지 활용할 일은 없더라도, 다음에 개인 서비스를 배포할 때는 실행 환경부터 좀 더 신경 써보고 싶다.

✅ 4L

👍 Liked | 좋았던 점

지난 프로젝트에서 겪었던 배포 문제와 이번에 배운 Docker, Kubernetes 개념이 자연스럽게 연결됐다. 단순히 새로운 기술을 배우는 것보다 실제 경험을 바탕으로 이해하니 기억에도 더 남는 것 같다.

🤔 Lacked | 부족했던 점

Docker와 Kubernetes의 역할은 이해했지만, 실제 서비스 규모에 따라 어떤 구성을 선택해야 하는지는 아직 판단하기 어렵다. 개념을 아는 것과 직접 운영하는 것 사이에는 차이가 있을 것 같다.

📚 Learned | 새롭게 배운 점

컨텍스트 엔지니어링은 AI에게 필요한 정보를 관리하는 과정이고, Agent Harness는 모델의 판단을 실제 실행으로 이어주는 구조라는 점을 정리했다. Docker와 Kubernetes의 역할 차이도 좀 더 명확해졌다.

🚀 Longed for | 앞으로 더 해보고 싶은 점

개인적으로 개발한 서비스에 Docker를 적용하고 AWS에 직접 배포해보고 싶다. 단순히 실행하는 데서 끝내지 않고 메모리 사용량이나 장애 상황까지 확인하면서 운영 경험을 쌓아보고 싶다.
